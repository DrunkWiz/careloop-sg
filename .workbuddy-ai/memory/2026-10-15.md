## Fixed: senior switcher "+ Set up someone new" loses caregiver ID

**Bug:** SeniorSwitcher's link was `<a href="/care/family/you?caregiver=">` — the caregiver ID was literally empty. CareApp used `params.has('caregiver')` which returns true even for empty values, so it tried `CaregiverApp caregiverId=""` → 404 → error screen with "Choose a demo family" link.

**Fix (Pairing.tsx + CareApp.tsx):**
1. SeniorSwitcher: changed `<a href>` to `<button onClick={() => navigate('/care/family/you')}>` — `navigate` preserves the current query string (caregiver ID + demo) automatically
2. Door logic: `params.has('caregiver')` → `params.get('caregiver')` (truthy check, so empty falls through to RoleChooser or contact-based FamilyApp)
3. CaregiverApp: added `useRoute(parseRoute)` — when a caregiver has no seniors and is on the settings route, renders `<Pairing caregiver={...}>` directly using the caregiver info from `cgView.caregiver`
4. Pairing.tsx: `view` is now optional; when only `caregiver` is passed (empty-seniors case), only the pair code form is shown (consent/family sections skipped)
5. Empty-seniors state: shows "Set up someone new" button that navigates to the You tab

Pair code is linked to the correct caregiver via `view.contact.caregiver_id` (normal case) or `caregiver.id` (empty-seniors case). New senior appears in switcher after pairing via the 15-second `useLive` refresh.

## Sibling Rota — full implementation

**New store kind:** `rota` (one per senior: `id`, `senior_id`, `mode` (weekly/daily), `start_date`, `order` (contact ids), `swaps`)
- `contracts/schemas/Rota.schema.json` created + example in `write_examples.py`
- Added `"rota"` to `KINDS` in `store.py`
- Contract test count: 12 → 13 examples
- **Contract change flagged for team OK**

**Engine (`backend/engine/ladder.py`):**
- `on_duty(store, senior, day)` → the contact on duty for this day, or None
  - weekly: `(days_since_start // 7) % len(order)`; daily: `days_since % len(order)`
  - swap for the exact date wins; contacts that don't exist or aren't linked to this senior are skipped
  - AAC-path seniors → None (rota ignored); no rota/empty order/before start → None
- `run_day()` targeting: rung R → ALL contacts (unchanged); every other rung → on-duty contact, else primary, else all (fallback). AAC seniors: rota ignored.
- Handovers still claimable by ANY linked caregiver (not just on-duty)

**API (`backend/api/app.py`):**
- `GET /senior/{sid}/rota` → rota + on_duty (404 if no senior)
- `PUT /senior/{sid}/rota` → set mode/start_date/order (400 if order has invalid/dup/AAC contact; 404 if no senior)
- `POST /senior/{sid}/rota/swap` → {date, contact_id} (same validation)
- `DELETE /senior/{sid}/rota` → back to primary behaviour
- `/care/family/{contact_id}` adds `on_duty` + `on_duty_name`
- `/care/caregiver/{id}` adds `on_duty` per senior

**Demo (`backend/api/demo.py`):**
- Mr Tan gets a weekly rota [tan-weiling, tan-kelvin] starting from demo start (40 days before today)
- On DEMO_TODAY (Oct 13), Kelvin is on duty (week 5, index 1)
- POST /demo/reset + /demo/advance {days: 11} still works; rung-4 goes to Kelvin (on duty); red flag reaches both

**Web:**

- Mock implementations in `mock.ts`; `on_duty`/`on_duty_name` in mock family + caregiver views
- "Who's on duty" badge in FamilyApp (`CareApp.tsx`) — green when you're on duty
